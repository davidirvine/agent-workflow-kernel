## ADDED Requirements

### Requirement: Sync is a deliberate kernel-version bump, never an unbounded HEAD pull

`scripts/sync-kernel.sh` SHALL compare the consuming app's `.kernel-version` file to the kernel's current version (read from `<kernel-repo>/.release-please-manifest.json`'s `"."` value) and report the upgrade path before making any change. If the app's version is greater than or equal to the kernel's version, the sync SHALL exit 0 as a no-op with an "up to date" message.

#### Scenario: Up-to-date app reports no-op

- **WHEN** an app whose `.kernel-version` equals the kernel's current `.release-please-manifest.json` `"."` value runs `sync-kernel.sh --kernel-repo <path>`
- **THEN** the script exits 0 and reports `up to date at <version>`, making no filesystem changes

#### Scenario: Sync reports the upgrade path before writing

- **WHEN** an app whose `.kernel-version` is less than the kernel's current version runs `sync-kernel.sh --kernel-repo <path>` (without `--dry-run`)
- **THEN** the script first reports `syncing <app-version> → <kernel-version>` and then applies the sync

### Requirement: `--dry-run` reports without writing

`sync-kernel.sh` SHALL accept a `--dry-run` flag. In dry-run mode it SHALL perform every read and computation (version comparison, copy plan, clobber detection) and emit a summary of what would change, then exit 0 without writing or modifying any file.

#### Scenario: Dry-run never writes

- **WHEN** `sync-kernel.sh --dry-run` runs in any state (up-to-date, behind, behind with conflicts)
- **THEN** no file in the consuming app is created, modified, or deleted; the script's output describes what a non-dry-run would do

### Requirement: Clobber-protection refuses to overwrite locally-modified synced files

`sync-kernel.sh` SHALL maintain `.kernel-sync-hashes.json` at the consuming app's root recording the SHA-256 of every synced file as of the last successful sync. Before overwriting any file with the kernel's version, the script SHALL compute the consuming-app file's current SHA-256 and compare it to the recorded hash. If they differ, the file was modified locally; the sync SHALL refuse, collect every conflicting path, report them at the end, and exit non-zero, unless `--accept-kernel` was passed.

#### Scenario: A locally-modified file blocks sync

- **WHEN** a consuming app has edited a kernel-synced file (e.g. `scripts/checks.sh`) since its last sync, and `sync-kernel.sh` runs without `--accept-kernel`
- **THEN** the script reports the conflicting path(s) and exits non-zero; the locally-modified file is not overwritten and no kernel file is written

#### Scenario: `--accept-kernel` overrides clobber-protection

- **WHEN** `sync-kernel.sh --accept-kernel` runs against an app with locally-modified synced files
- **THEN** the script overwrites the conflicting files with the kernel's versions, warns about each overwrite in its output, and writes the updated `.kernel-sync-hashes.json`

#### Scenario: A new kernel file is copied without conflict

- **WHEN** the kernel has added a file (path absent from the consuming app) since the last sync
- **THEN** the script copies the file; no conflict is possible (the consuming app has nothing to overwrite)

### Requirement: Sync refuses when `.kernel-sync-hashes.json` is absent; `--adopt-existing` is the explicit bootstrap

If the consuming app has no `.kernel-sync-hashes.json` (the app was scaffolded by hand, generated by a pre-slice-4 `new-app.sh`, or the file was deleted), `sync-kernel.sh` SHALL refuse to make any change and SHALL report that the app has no sync baseline, instructing the user to run with `--adopt-existing` to bootstrap. With `--adopt-existing`, the script SHALL compute the SHA-256 of every present kernel-tier and stack-tier file, write `.kernel-sync-hashes.json` from those hashes, write `.kernel-version` to the kernel's current version, and exit 0 without touching any other file in the consuming app.

#### Scenario: Sync refuses without a baseline

- **WHEN** `sync-kernel.sh` runs against a consuming app that has no `.kernel-sync-hashes.json` and `--adopt-existing` was not passed
- **THEN** the script exits non-zero with a message naming the missing file and instructing the user to run `--adopt-existing`; no file in the consuming app is created, modified, or deleted

#### Scenario: `--adopt-existing` records the current state as the baseline

- **WHEN** `sync-kernel.sh --adopt-existing` runs against a consuming app without a sync baseline
- **THEN** `.kernel-sync-hashes.json` is written containing the SHA-256 of every present kernel-/stack-tier file, `.kernel-version` is set to the kernel's current version, no other file in the consuming app is modified, and a subsequent `sync-kernel.sh` invocation operates as a normal sync from a real baseline

### Requirement: Sync mirrors generation's manifest semantics

`sync-kernel.sh` SHALL read `kernel-manifest.json` the same way `new-app.sh` does and apply the same rules: kernel-tier paths minus `kernel.excludeFromGenerate` are copied; stack-tier paths are flattened (stripping `presets/<preset>/`); the documented overlap set is preset-wins; `kernel.specs` and the preset's `specs` are copied verbatim; the preset's `appTemplates` are re-applied (with clobber protection). The preset's `instrumentStubs` SHALL NOT be re-applied on sync (the instrument is app-owned content after generation).

#### Scenario: `excludeFromGenerate` paths are not pushed on sync

- **WHEN** sync runs and the kernel manifest has `kernel.excludeFromGenerate` entries (e.g. `.github/workflows/**`)
- **THEN** none of the expanded exclusion set is copied into the consuming app

#### Scenario: `appTemplates` are re-applied on sync

- **WHEN** the kernel's preset has an updated `appTemplates` source (e.g. the app-tier CI template)
- **THEN** the corresponding target in the consuming app is updated (subject to clobber protection)

#### Scenario: `instrumentStubs` are never touched on sync

- **WHEN** sync runs against an app whose instrument paths (`src/param-schema.js`, etc.) have real content
- **THEN** the instrument files are not read, hashed, copied, or compared; the user's instrument is left intact

### Requirement: Sync is additive only

`sync-kernel.sh` SHALL NOT delete files from the consuming app. If a kernel-tier or stack-tier path that existed in a prior sync is no longer in the kernel's manifest, the script SHALL report the path as informational ("kernel no longer tracks; left in place") and leave it untouched.

#### Scenario: Kernel-removed path is reported, not deleted

- **WHEN** sync runs against an app that has a file at a path the kernel no longer tracks
- **THEN** the script reports the path in its summary as "no longer tracked by kernel; left in place" and the file remains in the consuming app

### Requirement: Successful sync updates `.kernel-version` and `.kernel-sync-hashes.json`

After a successful write phase (clean or `--accept-kernel`), `sync-kernel.sh` SHALL write `.kernel-version` to the kernel's current version and SHALL write `.kernel-sync-hashes.json` with the post-sync SHA-256 of every synced file plus a `"syncedAt"` field equal to the kernel's current version.

#### Scenario: State files reflect the just-completed sync

- **WHEN** sync completes successfully
- **THEN** `.kernel-version` contains the kernel's current version on a single line, and `.kernel-sync-hashes.json` lists every synced path with its post-sync SHA-256 and `"syncedAt"` matching `.kernel-version`
