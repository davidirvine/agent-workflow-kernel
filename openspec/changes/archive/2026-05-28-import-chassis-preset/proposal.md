## Why

The kernel now has working dev gates (slice 1), but no preset, no chassis source-of-truth, and no rules for what travels via `sync-kernel.sh`. Without those, slice 3 (`new-app.sh`) has nothing to emit, slice 4 (sync + setup) has nothing to sync, and slice 5 (smoke-app) has nothing to build. This slice (ROADMAP slice 2) brings synth-d's Phase-1 chassis into `presets/svelte-faust-synth/`, establishes the openspec tier partitioning + sync manifest, parameterizes donor identity, and ships a deliberately **minimal** reference instrument (single droning oscillator) so the preset is buildable in isolation and the chassis seam is illustrated by example.

## What Changes

- Add **`presets/svelte-faust-synth/`** — the chassis (`Shell`, generic components, `param-schema.js` with the reference instrument's schema, store machinery, audio engine, MIDI, keyboard, patches storage), tokenized component CSS + `theme.css`, the FAUST DSP, and the preset's own `package.json` / vite+svelte config so it is a **self-contained buildable unit**. Following ROADMAP's locked decisions, the preset's own `.prettierrc` carries the Svelte plugin (the root config, trimmed in slice 1, does not).
- **Minimal reference instrument** (not synth-d's full subtractive synth): a single oscillator with a **waveform selector** (`kind: 'switch'`) and a **frequency knob** (`kind: 'knob'`, `ccScalable: true`) that owns the resting pitch. **Held keys override pitch via `gate`** (`pitch = gate ? freq : knobFreq`); the instrument **drones** (no envelope) so the knob's pitch is audible when no key is held, exposes `outputPeak` so the chassis scope/LED light up, and **honors the chassis power-off-silence lifecycle** — the path a gated instrument never exercises. `new-app.sh` (slice 3) blanks it when generating a fresh app; the preset keeps it as a worked example.
- **Bring chassis-architecture + chassis-theming specs** from synth-d into `openspec/specs/`, adapted for kernel tier (the Phase-1-only "refactor preserves synth behavior" / "pixel-identically to pre-tokenization" requirements are dropped — they describe a one-time migration, not an ongoing rule).
- **Introduce `preset-portability` capability:** the tier frontmatter convention (`tier: kernel | stack | instrument`) on every spec, the **sync manifest** format that `sync-kernel.sh` (slice 4) will consume to know what travels, the rule that no chassis/preset file may carry **donor identity** (the `synth-d:` localStorage namespace in chassis `patches/storage.js`, GitHub URLs, deploy paths, package name), and the contract that the preset is self-contained and buildable.
- **Parameterize the chassis identity leak point:** `patches/storage.js`'s `synth-d:` namespace becomes a **`__APP_NAMESPACE__` token** (or equivalent) the preset carries; `new-app.sh` in slice 3 injects the new app's namespace; an identity-leak check asserts no raw `synth-d:` remains in chassis or preset files.
- **CI gains the FAUST toolchain** and gets two new jobs alongside slice 1's lint/format job: a **preset-build** job (`npm ci && npm build` inside `presets/svelte-faust-synth/`) and an **extraction-audit / identity-leak** job that runs the slice's leak checks. The `smoke-app` job stays a stub — slice 5 turns it on.
- **One-time chassis-purity extraction audit** runs during implementation: the audit's forbidden-name list is **synth-d's full subtractive param vocabulary** (committed as a fixture in the change directory for reproducibility, archived with the change). This audit is what catches residual `cutoff`/`osc1Level`/`reverbMix` leaks the otherwise schema-derived test cannot see once the reference instrument's minimal schema is in place. A separate **traveling chassis-purity test** ships with the preset and runs in the preset-build job — schema-derived against the current schema, "vacuous-but-correct" against the minimal reference, strengthening as a downstream app adds its own params.

## Capabilities

### New Capabilities

- `chassis-architecture`: the chassis ↔ instrument seam — universal engine param contract (`freq`/`gate`/`modWheel`/`mixerPeak`/`outputPeak`), parameter-schema as the single source of truth, schema-derived store/UI collections, generic `Shell` with no instrument imports (except the schema module), and the executable chassis-purity test.
- `chassis-theming`: the chassis visual seam — two-layer CSS-token system (palette → component tokens), a single `theme.css` override point, chassis components contain no hardcoded identity color literals, and the token catalog is a versioned styling contract.
- `preset-portability`: spec tier frontmatter, the sync manifest format, the rule that the preset carries no donor-identity literals (`synth-d:` namespace parameterized via a token), the requirement that the preset is a self-contained buildable unit, and the minimum contract a preset's reference instrument must honor (exercises both store-backed descriptor kinds + the CC path + the chassis power-lifecycle).
